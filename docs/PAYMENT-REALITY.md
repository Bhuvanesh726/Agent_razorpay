# Payment reality: what is real and what is simulated

This document exists because the application's own records are not evidence for the
application's own claim. Our database will say an order is `PAID`, the audit trail
will show a clean `payment_succeeded` chain, and the test suite will pass — none of
which proves that money moved through Razorpay. Only Razorpay can settle that.

So the claim here is stated against Razorpay's live API, and you can re-run the check
yourself:

```bash
cd backend
python scripts/verify_payments.py
```

It walks every order and payment in the database, asks Razorpay's API about each one,
and prints `REAL` or `NOT IN RAZORPAY` per row. It is read-only.

**Result of the run at time of writing: 24 of 25 orders real in Razorpay; 23 of the 24
recorded payments not found there.**

---

## What is real

**Order creation — all of it.** Every `razorpay_order_id` in the database was created by
a genuine API call to Razorpay (`app/payments/gateway.py::create_order`) and is fetchable
from their API right now. 24 of 25 orders verify; the one exception (#3) never got as far
as calling Razorpay.

**The Layer 2 browser checkout — a genuine card payment.** Order #1 was paid through
Razorpay Checkout by a human entering real test-card details and completing the OTP step,
with the callback signature verified server-side:

```
Order #1   order_TXCXeCdpxCX5JC   →  REAL   status=paid   attempts=4
           pay_TXCrkCuqeuCx7h     →  REAL   status=captured  method=card  amount=2800  captured=True
```

`attempts=4` is the human fumbling through the form. This is the end-to-end path working
exactly as intended: real order, real instrument, real capture, real HMAC verification.

**A second real payment — captured by Razorpay, missed by us.** Order #23 has a genuine
captured wallet payment at Razorpay that our database records as `FAILED`:

```
Order #23  order_TXfZQkkyfBle74   →  REAL   status=paid   attempts=1
           pay_TXfb1zHIyG3lUd     →  REAL   status=captured  method=wallet  amount=27500  captured=True
           (our DB: status=FAILED, razorpay_payment_id=None)
```

This is a reconciliation bug, not a simulation. It is written up in full in `Failures.md`
(Layer 5, entry 2) — a failure callback arrived before a success callback, and the order
state machine forbids `FAILED → PAID`, so a verified success was silently dropped. Counted
honestly, there are **two** real captured payments in Razorpay, not one; the verification
script reports one because the second one's id was never recorded on our side.

**The UPI Autopay mandate — real authorization, real network-enforced cap.** A ₹1
authorization transaction was completed through Razorpay Checkout, producing a confirmed
recurring mandate:

```
pay_TXgOsxlV5Y4eiU   →  REAL   status=captured  method=upi  amount=100
token_TXgOt6JXr9loU4 →  recurring=true  status=confirmed  amount_blocked=500000 (₹5,000)
```

Razorpay's own checkout screen stated the terms: *"a payment of ₹1 will be charged now…
may then charge up to ₹5,000 anytime until 3 Sep 2031."* The ceiling is enforced by the
payment network, not merely by our policy engine. This mandate was created by a spike
script and is not wired into the product.

## What is simulated

**Every other captured payment.** Four families of locally-minted ids appear in the
database — `pay_demo_*`, `pay_demo_retry_*`, `pay_test_*`, and `pay_auto_*`. None exist at
Razorpay. Each was generated by this backend, signed with the merchant secret, and then
passed through the *real* signature check — which necessarily passes, because it is
verifying our own signature. `mark_paid` then records a capture that never happened.

Two code paths produce them:

| Path | Ids | Where |
|---|---|---|
| Dev completion endpoint (pre-existing) | `pay_test_*`, `pay_demo*` | `app/routers/payments.py::test_complete_payment` (gated on `APP_ENV=development`) |
| Autonomous agent capture (Layer 5) | `pay_auto_*` | `app/agent/harness.py::_auto_complete_agent_payment` |

The signature verification in both is genuine and unmodified; only the *signing* is
synthetic. That distinction is worth keeping — the verification code path is real and
tested — but it does not make the payment real.

## Why the simulated path exists

Not as a shortcut taken for convenience. Two concrete blockers, both verified rather than
assumed:

1. **Razorpay's public API has no headless third-party checkout completion.** Capturing a
   payment requires a human driving Razorpay's Checkout iframe (card entry, OTP, or a UPI
   app approval). An autonomous agent has no browser. This is precisely why the
   pre-existing `test-complete` endpoint was written, and its docstring says so.
2. **On-demand server-side charging is not enabled on this account.** The correct
   production mechanism is a mandate plus `POST /v1/payments/create/recurring`. The mandate
   half works (proven above). The charge half returns:
   ```
   POST /v1/payments/create/recurring  →  400  "The requested URL was not found on the server."
   POST /v1/payments/create/upi        →  400  "The requested URL was not found on the server."
   ```
   Razorpay gates this per-account; it is not a dashboard toggle (the whole settings area
   was checked). It requires account activation plus a support request, which could not be
   obtained before the deadline.

So the mandate proves the *authorization* primitive end to end, and the missing piece is
strictly the *charge* call — roughly twenty lines behind a support ticket, not an
architectural gap.

## What this project actually demonstrates

An agent that is **granted bounded authority and provably held to it**: scoped tools, a
spend limit enforced both by the policy engine and (via the mandate) by the payment
network, a policy checkpoint that no agent can bypass, and an append-only audit trail that
distinguishes *how* each purchase was confirmed. The order side of the payment rail is
real throughout, and one genuine card checkout and one genuine wallet capture exist.

What it does not yet demonstrate is an agent moving money without a human in the loop.
That last hop is exactly the primitive that emerging agent-payment standards — **ACP**,
**AP2**, and **x402** — are being designed to provide: a way for an authenticated,
constrained agent to present proof of delegated authority and settle a payment
programmatically, without a browser and without the merchant handing the agent raw
credentials. This codebase builds everything up to that boundary and stops there, honestly,
rather than dressing a local signature up as a settlement.
